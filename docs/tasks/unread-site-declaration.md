# Say when a site declaration is not being read

## The problem

A site whose render-facing declaration plates cannot see builds anyway, silently,
and the result looks like a rendering bug rather than a configuration one.

With no front page, `plan_site` anchors the site at the archive root and the render
layer synthesizes an index from the site's entries;
with no shell and no stylesheet, that index comes out in the built-in shell.
The page a person gets is a title, a description, an `<ul class="entry-list">` and *Generated by plates* —
which is exactly what a correctly-configured site with one entry looks like,
so there is nothing on the page to suggest the declaration was the problem.

Nothing on the way there says a word.
[`read_term_config`](/plates/src/term.rs) returns `TermConfig::default()`
for a field with no spec, a field with no `vocabulary:`, a vocabulary that is not reified,
and a reified vocabulary with no node for the gate's value —
four distinct causes, one silent answer.
`specs_from_exports` in [`plates-cli`](/plates-cli/src/config.rs) reads
`label`, `gate`, `view` and `hold` off an export entry and ignores every other key without comment.

## Repro

The `diaryx` archive, before 2026-09-07.
Its `.config/config.yaml` carried

```yaml
fields:
  audience: { type: str, values: closed, vocabulary: audiences.yaml }
exports:
  diaryx:
    label: Diaryx
    gate: { field: audience, value: public }
    shell: .config/sites/diaryx/shell.html
    stylesheet: .config/sites/diaryx/style.css
```

with the front page under the app's own `diaryx.site_index.diaryx`.
That is the diaryx application's dialect, and the application reads it correctly.
`plates build` over the same archive reported `✓ diaryx — 18 pages` and wrote a synthesized
index in the built-in shell, having read none of the three keys that decide what the site looks like.

## What silence is for, and where it stops

[`term.rs`](/plates/src/term.rs)'s "Silence is the diagnosis" is about the *gate*:
an unknown value on a closed field is `prov check`'s `UnknownTerm` finding,
and repeating it here would say the same thing twice in worse words.
That argument holds. It does not cover an export entry carrying keys plates
used to read and no longer does, because nothing else reports those at all —
prov does not lint keys outside its own vocabulary, and by design it should not.

The distinction to keep: say nothing about an archive that never declared a render config,
which is most of them; say something about one that declared it somewhere plates is not looking.

## Done when

- An export entry carrying `shell`, `stylesheet`, `lang`, `syntaxes`, `index` or `front_page`
  produces a warning naming the key, the term node those settings belong on,
  and what the site fell back to without them.
- A site whose gate field declares a vocabulary that is **not** reified,
  or is reified with no node for the gate's value, warns once — with the two cases told apart,
  since the fix differs (`reify: true` on the field, versus a node for the term).
- A site with no front page from any source is reported as anchored at the archive root
  with a synthesized index, so the fallback is visible rather than inferred from the output.
- An archive that declares nothing render-facing anywhere stays silent.
