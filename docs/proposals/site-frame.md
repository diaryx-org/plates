# The site frame

## Status

Implemented, all four steps at once — they share the one restructuring of the
render pipeline that reads every source's metadata before it renders any body,
which is what lets a body's `prev`/`next` be the pager's. Three things landed
differently from the text below:

- **The outline is a fixed rail at `≥ 88rem`**, not 80: that is the width at
  which a 12rem rail fits beside the 44rem measure and the 16rem sidebar with
  the margins the layout already leaves. Below it the `<details>` is written
  `open` — a reader with scripting off gets everything — and the built-in script
  closes it, so a long outline does not push the prose down a phone.
- **`headings` in a body's own context costs a second expansion**, since a
  page's headings are not known until its template has run. Only a body that
  names `headings` pays it.
- **A destination `href` survives link rewriting.** `[x]({{e.href}})` had
  always been resolved as a *source* path, found nowhere, and stripped to an
  unpublished span — the header and footer examples below would have rendered
  every link inert. A source path is still tried first, then a destination.

The pager reads the forest continuously, as the nav does. A per-page `header:`
is still not designed.

## Summary

The default template publishes a readable page and an unhelpful site. The
sidebar is one fully expanded tree with the site's name as its first row; a
page has no anchors, no outline and no way to the next page; and the only
things a site can put around its content are a whole replacement shell or a
line crediting the generator. This proposes, in order of leverage:

1. **Heading anchors and an outline.** Every heading gets an `id` and a link
   to itself, in all three grammars; the outline becomes a `toc` shell slot,
   a `headings` list in the body context, and an "On this page" block in the
   built-in shell.
2. **A sidebar that is a sidebar.** A masthead naming the site, the tree
   starting at the front page's children, sections that collapse to the
   current branch, a pager to the previous and next page, and a mobile drawer
   whose button says what it is.
3. **A header and a footer that are documents.** `site.header` and
   `site.footer` name Markdown documents on the term node, rendered through
   the same pipeline a body is — templating, `:vis`, link rewriting — into
   `site_header` and `site_footer` slots. A site gets a masthead, a tagline,
   a licence line and a "recent entries" list without writing a shell, and
   with no new template syntax.

Nothing here adds a template engine, a directive, or a config vocabulary.
Every addition is a slot, a frontmatter key already shaped like its
neighbours, or a document.

## What a reader meets today

Rendered from this repository's own archive, with nothing configured:

- **The sidebar is the tree, and the tree includes the root.** `plates` is
  the first `<li>`, its seven children indented beneath it behind a guide
  line, so every entry on the site sits one level deeper than it is. A site
  with three levels of real hierarchy shows four.
- **Every branch is open on every page.** `build_site_nav_tree` is capped at
  six levels and hides nothing below that; a vault with forty pages under six
  sections lists all forty on every page, and the current one is a tinted row
  somewhere in the middle. The tint is the only orientation the reader has.
- **The site's name is a nav row.** `ShellSlots::site_title` exists and the
  built-in shell never uses it. There is no masthead, no home link outside
  the tree, and nowhere for a tagline or a link out.
- **A page is a wall.** Headings render as bare `<h2>` — twig writes no
  `id`, and this crate adds none — so a heading cannot be linked to, a long
  README has no outline, and `nav.toc` in the stylesheet is only ever filled
  by the single-file renderer. The proposals on this site are 300–450 lines
  each.
- **There is no next.** A tree-shaped site is a book, and a page in it has no
  link to the page after it. The reader's only route onward is back to the
  sidebar.
- **The drawer's button lies.** `nav-toggle` is written with
  `aria-expanded="false"` and the script toggles a class without ever
  updating it. It has no `aria-controls`, no visible label, Escape does not
  close the drawer, and there is no skip link past it.
- **A footer is a credit.** `footer` holds "Generated by …" or nothing. A
  licence line, a copyright, a link to the source: each means replacing the
  whole shell.
- **A shell cannot find home.** The slots carry pre-prefixed hrefs inside
  `head` and `site_nav`, but a template that writes its own `<a href>` to the
  front page has no way to know how deep the current page is.

## Within the page: anchors and an outline

### Every heading gets an `id`

A pass over the rendered HTML, after twig and before link rewriting, on the
precedent `syntax::highlight_code_blocks` set: twig's serializer offers no
heading-id option, and a pass over the output covers Markdown, Djot and HTML
bodies with one implementation. `verbatim` pages skip it as they skip
everything.

For each `<h1>`–`<h6>` without an `id`: the id is `prov::link::slug` of the
heading's text — the same function `title_to_anchor` uses, so a single-file
render and a site render agree on what `## Status` is called — and a second
heading with the same slug on one page gets `-2`, `-3`. A heading that
already carries an `id` (an HTML body, a Djot `{#custom}` attribute) keeps
it. An anchor link is appended inside the heading:

```html
<h2 id="status">Status <a class="heading-anchor" href="#status" aria-label="Link to this section">#</a></h2>
```

Inside rather than beside, so the heading's text is what a screen reader
reads first and the link is one tab stop after it. The stylesheet hides the
mark until the heading is hovered or the link focused.

### The outline is data before it is markup

The pass returns `Vec<Heading { level, id, text }>` alongside the HTML. That
list is:

- **`{{{toc}}}`**, a new raw shell slot: `<nav class="toc" aria-label="On
  this page">` holding a nested list of the page's `h2`–`h3` headings, or
  empty when there are fewer than two. A template puts it where it wants
  it; the built-in shell puts it in a right-hand rail at widths where there
  is room for one and in a `<details>` above the content otherwise.
- **`headings`** in the body template context, each `{level, id, text}`, so
  a page that wants its outline spelled its own way writes
  `:::each{of=headings as=h}` and a link to `{{h.id}}`. This is why the pass
  runs *after* templating and not before: a template that generates its
  headings still gets them listed.

A page turns it off with `toc: false` in frontmatter, on the pattern
`hide_from_nav` set; a site-wide default is a stylesheet decision (`.toc {
display: none }`) rather than a key, until a site turns out to need the key.

## The sidebar

### A masthead, then the tree

The front page leaves the tree. The built-in shell writes:

```html
<nav class="site-nav" aria-label="Site navigation">
  <a class="site-masthead" href="{{root_prefix}}index.html">{{site_title}}</a>
  <ul class="nav-list">…the root's children…</ul>
</nav>
```

`render_site_nav` lists the root node's children rather than the root, and
marks the masthead `aria-current="page"` on the front page. The tree loses a
level everywhere, the guide line starts at the first *nested* list, and the
site's name becomes what a site's name is on every other site: the link home
at the top left.

A **`root_prefix`** text slot is added so a caller's shell can do the same
(`href="{{root_prefix}}index.html"`), and for the stylesheet or logo a
hand-written shell links itself. It is the one value every prefixed href in
`head` and `site_nav` was already computed from, exposed rather than
duplicated.

### Sections collapse to the current branch

A node with children renders as a disclosure:

```html
<li class="nav-section nav-ancestor">
  <details open>
    <summary><a href="…">plates-render</a></summary>
    <ul class="nav-list">…</ul>
  </details>
</li>
```

`open` is written on the current page's ancestors and on the current page's
own node; every other section starts closed. The whole tree is still in the
HTML — crawlable, printable, searchable with the browser's find, and correct
with scripting off — and a reader sees the branch they are in plus the names
of the others. No state is stored anywhere: which sections are open is a
function of which page this is, which is what makes the answer the same for
every reader and every build.

The link and the disclosure are separate targets. Clicking the title goes to
the section's page; clicking the chevron `<summary>` draws opens it. This is
the one place the built-in stylesheet needs a marker of its own, since the
user-agent triangle sits before the text and reads as a bullet.

The sidebar also scrolls the current entry into view on load — three lines of
the existing script, `nav.querySelector('[aria-current]')?.scrollIntoView({block: 'center'})`
— so a long tree opens on the reader's place rather than its top.

### A pager

Below the content, the previous and next page in the tree's reading order —
the depth-first order the sidebar already lists — as a **`{{{pager}}}`** raw
slot:

```html
<nav class="pager" aria-label="Pager">
  <a class="pager-prev" rel="prev" href="…"><span>Previous</span> plates</a>
  <a class="pager-next" rel="next" href="…"><span>Next</span> plates-cli</a>
</nav>
```

`rel="prev"`/`rel="next"` are what a reader-mode and a search engine read a
sequence off. A forest has one reading order because the nav has one: the
front page, then its subtree, then each orphan root in the order
`build_site_nav_tree` places them. A `hide_from_nav` page is in no sequence
and gets no pager, since the tree it would be read through does not hold it.
Under a grouped arrangement the order is the groups', which is what a reader
of a dated site expects the next page to be.

`prev`/`next` also join the body context as entries, so a template can spell
its own.

### The drawer

Below the breakpoint the built-in shell writes a bar rather than a floating
button:

```html
<header class="site-bar">
  <button class="nav-toggle" aria-controls="site-nav" aria-expanded="false">Menu</button>
  <a class="site-masthead" href="…">plates</a>
</header>
```

The script sets `aria-expanded` to match the drawer, closes it on Escape and
returns focus to the button, and the drawer gets `id="site-nav"` so the
`aria-controls` names something. A `<a class="skip-link" href="#content">Skip
to content</a>` is the first thing in `<body>`, visible only when focused,
and `<main>` gains `id="content"`. None of this changes the desktop layout;
the bar is the mobile spelling of the masthead.

## The frame: a header and a footer that are documents

### The shape

Two keys on the term node beside `shell` and `stylesheet`:

```yaml
site:
  shell: .config/sites/docs/shell.html      # optional, as now
  header: .config/sites/docs/header.md      # new
  footer: .config/sites/docs/footer.md      # new
```

Each names a Markdown (or Djot, or HTML) document, read by `read_theme`
exactly as the shell is — as text, reported and ignored when missing — and
rendered **per page** through the body pipeline: template expansion against
the page's context, `:vis` filtering for the site's audience, twig, link
rewriting to the page's depth. The result fills two new raw slots,
**`site_header`** and **`site_footer`**. The existing `footer` slot keeps
meaning the attribution line; the built-in shell writes `site_footer` and
then `footer` inside one `<footer>`.

A footer, then, is this:

```markdown
© :val[site.title] · [Source](https://github.com/diaryx-org/plates) · MIT or Apache-2.0

:::vis{.public}
Latest: [:val[entries.0.title]]({{entries.0.href}})
:::
```

and a header is a one-line tagline, or a row of links to the site's top
sections written as an ordinary list, styled by the sheet as a bar.

### Why documents and not shell partials

The obvious spelling is `{{> header}}` in the shell. It is refused for the
reason the shell refused Handlebars: the substitutor is named slots and
nothing else, because a shell is an HTML document whose scripts and styles
are full of braces, and every operator added to it is one more thing an
inline script must not happen to contain. A partial would also be HTML — a
thing an editor over the archive cannot edit, and a thing the gate cannot
filter.

A document is already everything a header needs to be. It has the template
vocabulary, so it can name the site, the page and the entries. It has `:vis`,
so one footer can carry a line only one audience sees. Its links are rewritten
like any body's, so `[About](/about.md)` works from a page at any depth and
goes inert if `about.md` is not published. And it is a file under
`.config/sites/<name>/` beside the shell and the sheet, which is where a
site's frame already lives.

The header and the footer are **not** entries: they are excluded from the
render set the way a shell is, so they never publish as pages of their own,
never appear in the nav, and cannot be linked to. That is the same exclusion
`template:` resolution will need, and this is the first key to need it.

### What the built-in shell does with them

```html
<body class="has-site-nav">
  <a class="skip-link" href="#content">Skip to content</a>
  {{{site_nav}}}
  <div class="site-content">
    <header class="site-header">{{{site_header}}}</header>
    <main id="content">
      <article>
        {{{breadcrumbs}}}
        {{{toc}}}
        <div class="content">{{{content}}}</div>
      </article>
      {{{pager}}}
    </main>
    <footer class="site-footer">{{{site_footer}}}{{{footer}}}</footer>
  </div>
  {{{scripts}}}
</body>
```

An empty slot writes an empty element, which the sheet collapses (`:empty {
display: none }`), so a site that declares neither key publishes exactly the
frame it publishes today, one masthead and one pager richer.

## What is not proposed

- **A `nav:` document override.** An authored Markdown list in place of the
  generated tree is tempting and loses the one thing the tree guarantees —
  every published page appears in it exactly once, a test-pinned invariant.
  A site that wants a curated menu writes it in `site.header`; the tree
  stays the tree.
- **Search.** A static index is a different proposal with a different
  dependency footprint.
- **Persisting which sections a reader opened.** Local storage across pages
  means the sidebar differs between two readers of one build, and the
  current-branch rule already opens what a reader most often wants.
- **A `{{#if}}` in the shell.** Every conditional a shell has wanted so far
  is "this slot is empty", and an empty element a stylesheet hides is the
  answer without an operator.

## Sequencing

Each lands on its own and nothing waits on anything later:

1. Heading ids and anchors, `toc` slot, `headings` in context, `toc: false`.
   Stylesheet: `.heading-anchor`, `.toc` as a rail. Purely additive to the
   shell; a caller's template that never names `toc` is unchanged.
2. Masthead, root-less tree, `root_prefix` slot, collapsing sections, scroll
   into view, the `aria-expanded`/Escape/skip-link fixes. **Behavioural
   change** to `site_nav`'s markup, which a caller's stylesheet may style.
3. `pager` slot, `prev`/`next` in context.
4. `site.header`/`site.footer`, `site_header`/`site_footer` slots, and the
   render-set exclusion. Adds two fields to `SiteSpec`, `TermConfig`,
   `SiteTheme` and `SiteOptions`; none is `non_exhaustive`, so a struct-literal
   caller names them.

Every step is a change to the built-in shell's bytes. The
`the_built_in_shell_is_unchanged` test is the record of what a page contains,
and it is updated, not weakened, at each step.

## Open questions

- **Where the outline goes at width.** A rail beside the content is what a
  reader of documentation expects; a block above it is what a reader of an
  essay does. The built-in shell has to pick one, and the sheet's breakpoint
  is the whole of the decision. A rail at `≥ 80rem`, a `<details>` below, is
  the working answer.
- **The pager under a forest.** Whether the last page of the front page's
  subtree points "next" at the first orphan root, or the sequence ends at
  the subtree's edge and each orphan is its own book. The nav lists them
  continuously, so the pager should too, but it is the one place a reader
  could feel the seam.
- **A per-page header.** `header:` in a page's frontmatter, on the pattern
  `shell:` set, is one more key and no new mechanism. Not needed for a first
  cut; noted so it is not designed twice.
